# Ripple Live Android — GPT Live 对齐体验设计

日期：2026-08-08

状态：C 高保真交互与动效方向已确认，尚未开始实现

## 1. 目标

把 Ripple Live 设计成一个以语音为第一入口、可通过镜头理解现实、并能把对话转化为记忆与待办的私人助理。

本次设计重点不是增加更多首页功能，而是让以下链路连续、自然且可信：

`开始说话 → 必要时打开镜头 → 获得语音与视觉结果 → 明确保存或执行 → 回到可继续的对话`

整体体验参考 GPT Live 的沉浸式实时感、克制界面和状态动效，但 Ripple Live 保留自己的记忆、待办和视觉内容能力。

## 2. 产品原则

1. **语音优先**：打开应用后，用户应能在一次点击内开始说话。
2. **镜头由用户决定**：相机永不自动开启，只能由用户主动点击。
3. **明确保存**：只有用户明确说“记住这个”或点击保存时才创建记忆，不自动保存，也不频繁追问。
4. **执行必须有回执**：创建待办、保存记忆或完成工具动作后，必须给出简短、明确的成功或失败反馈。
5. **实时结果不断流**：工具结果和视觉卡片出现时，语音回答继续，不切换到新的全屏页面。
6. **会话连续**：一次语音或视频通话结束后，内容仍属于同一条对话，并能继续用语音进入。
7. **不伪装能力**：界面不得暗示尚未实现的持续视频理解、后台通话或真正全双工对话。

## 3. 全局信息架构

底部使用四个固定入口：

1. **对话**：默认首页、语音/视频入口、当前与历史对话。
2. **记忆**：显式保存的文字、图片与视觉记忆。
3. **待办**：未完成、已完成和带提醒时间的任务。
4. **我的**：账户、连接状态和已经真实可用的体验设置；不预放音色或智能等级等占位入口。

首页不展示仪表盘、统计数字或最近内容卡片。首页的唯一主任务是“开始说话”，相机是次要入口。

### 3.1 对话首页

- 中央为 GPT Live 风格的冷蓝软体核心。
- 主文案使用一句简短提示，例如“想聊点什么？”或“我在听”。
- 主操作是语音按钮；相机按钮与其并列但视觉权重更低。
- 历史对话从页面上方或轻量入口进入，不在首页堆叠卡片。
- 底部四栏导航始终可见；进入实时通话后隐藏。

## 4. 视觉系统

### 4.1 色彩

- 背景：接近纯黑的冷色黑，避免泛灰和暖黑。
- 主体高光：冰白色。
- 主体中间色：浅蓝、天蓝。
- 深部阴影：深海蓝。
- 边缘光：少量青蓝色，只用于表达实时状态。
- 紫色不作为主色使用。
- 危险或结束操作保留低饱和红色。

### 4.2 形态

- 语音模式的软体核心是唯一视觉中心。
- 形态应有连续、自然的体积变化，不能像等比例缩放的圆球。
- 卡片、字幕和回执均使用大圆角、半透明冷黑与轻度背景模糊。
- 图标使用线性、简洁、接近系统原生的风格。

### 4.3 排版与内容

- 文案短、直接，不解释界面本身。
- 实时状态以“正在听”“正在思考”“正在回答”等动词表达。
- 不长期显示大段实时转写；默认只保留最近一句字幕。
- 完整内容在通话结束后进入对话记录。

## 5. 语音实时模式

### 5.1 状态

| 状态 | 视觉表现 | 文案与行为 |
| --- | --- | --- |
| 待机 | 软体缓慢呼吸，亮度低 | “想聊点什么？” |
| 连接中 | 核心收紧，边缘光缓慢旋转 | “正在连接” |
| 聆听 | 体积随输入音量轻微变化，边缘更亮 | “正在听” |
| 思考 | 动作减慢并向内部收束 | “正在思考” |
| 工具调用 | 核心缩小，底部出现紧凑状态或结果卡 | “正在查询天气”等 |
| 回答 | 形态与输出音量联动，变化更有节奏 | 临时显示回答字幕 |
| 错误 | 动效停止，显示明确恢复操作 | “连接中断，点击重试” |

视觉层不得维护第二套互相独立的会话状态。现有实时状态按以下规则映射：

| 现有会话状态 | 视觉状态 |
| --- | --- |
| `idle` | 待机 |
| `connecting`、`preparing` | 连接中 |
| `listening` | 聆听 |
| `thinking` | 思考 |
| `using_tool` | 工具调用 |
| `speaking` | 回答 |
| `ended` | 结束转场后退出实时界面 |
| `error` | 错误 |

### 5.2 动效参数方向

- 待机呼吸周期约 2.4–3.0 秒，亮度和体积变化不超过 8%。
- 控件按下反馈在 90 毫秒内发生，使用轻微缩放和亮度变化，不触发大范围涟漪。
- 普通状态切换使用约 280 毫秒的形态过渡，曲线以前快后慢为主。
- 聆听变化快速但幅度克制；麦克风能量先经过平滑和峰值衰减，避免逐采样点抖动。
- 思考状态以整体收紧、内部光迁移和低速旋转为主，不使用加载圆环。
- 回答状态与实际播放音量关联；输出停顿时自然回落，不播放与音频无关的固定循环。
- 用户开启或关闭镜头时，软体核心和相机画面在约 420 毫秒内完成交接，不进行硬切。
- 回答字幕在音频对应片段结束后停留约 1.8 秒再淡出；新字幕到来时直接平滑替换。
- 系统开启“减少动态效果”时，改为亮度和轻微缩放变化。

### 5.3 打断与字幕

- 用户直接开口即可打断当前回答，利用现有自动取消能力。
- 检测到有效打断后，输出状态在 120–180 毫秒内完成视觉“泄压”，随即切回聆听状态。
- 打断必须先触发现有 response cancel 和本地音频停止，再更新为聆听状态，不能只切换动画。
- “手掌打断”不再作为主按钮，可放入更多操作或无障碍辅助位置。交互原型中的打断按钮仅用于模拟真实语音事件，不属于正式控制栏。
- 字幕默认只显示最近一句，回答结束后淡出。
- 提供字幕开关；关闭字幕不影响最终对话记录。

### 5.4 C 高保真软体核心

软体核心使用实时渲染而不是预录视频或固定 Lottie 动画。渲染器只负责视觉，状态机负责业务语义，两者通过受控参数连接。

状态机向渲染器提供：

- `state`：待机、连接、聆听、思考、工具、回答、错误。
- `inputLevel`：经过平滑处理的麦克风能量。
- `outputLevel`：当前实际播放音量。
- `transitionProgress`：状态切换或相机转场进度。
- `reducedMotion`：系统减少动态效果设置。
- `qualityTier`：高质量或省电模式。

渲染器输出冷蓝软体、内部光迁移、边缘辉光和轻量形态变化，但不得自行推断业务状态。

默认使用高质量模式并以 60fps 为目标。若连续约 2 秒的实际帧率低于 45fps、设备进入省电模式或出现明显发热，则降级到 30fps：减少软体分层、模糊采样和噪声复杂度，但保持状态、色彩与转场时序一致。恢复高质量模式应有滞后，避免反复切换。

Android 实现应优先使用 GPU 友好的单画布或单渲染面方案，避免多个大面积实时模糊层叠加。软体失败或图形上下文丢失时，回退为静态冷蓝核心加亮度呼吸，不影响语音会话。

### 5.5 语音一轮的完整动效编排

1. 用户点击开始：按钮在 90 毫秒内反馈，首页元素淡出，软体核心收紧并进入连接状态。
2. 连接成功：约 280 毫秒过渡到聆听，文案变为“正在听”。
3. 用户说话：软体外轮廓跟随平滑后的输入能量，字幕仅显示最新识别片段。
4. 语义停顿成立：软体在约 280 毫秒内向内收束，进入思考。
5. 工具调用：核心上移并缩小至约 65%，结果层从底部进入；音频播放不因卡片出现而停止。
6. 助手回答：核心恢复主位置并跟随真实输出音量；工具卡可继续保留，直到结果不再需要。
7. 用户插话：立即取消输出，核心快速泄压并回到聆听；旧字幕淡出，新用户字幕接管。
8. 用户结束：核心与控制栏淡出，返回同一条对话时间线。

## 6. 视频模式（已选 A：全屏画面）

### 6.1 布局

- 相机画面占满屏幕，真实世界是唯一视觉中心。
- 顶部左侧显示“镜头已开启”与当前识别状态。
- 顶部右侧提供前后镜头切换。
- 中部仅在必要时显示轻量识别框，不长期保留。
- 回答字幕位于底部操作栏上方，停止说话后淡出。
- 底部固定保留镜头、麦克风/字幕和结束通话操作。
- 视频模式不叠加大型软体核心，以免遮挡目标物体。

正式底部控制栏不设置单独的“打断”按钮。默认包含镜头开关、麦克风静音或字幕入口，以及结束通话；自然打断由用户直接开口触发。

### 6.2 语音与相机转场

1. 只有用户点击镜头按钮后才申请权限并启动相机。
2. 权限确认前，软体保持语音状态并显示轻量准备提示，不提前展示黑色相机层。
3. 首帧可用后，软体在约 420 毫秒内缩小、降低亮度并淡出；相机画面同时由轻微放大回到 100%。
4. 相机接管后，顶部出现“镜头已开启”，底部控制栏保持位置稳定。
5. 服务端真实请求单帧时，才短暂出现识别状态或轻量取景框。
6. 用户关闭镜头后，相机画面淡出，软体从低亮度小形态恢复到当前语音状态。
7. 权限拒绝、首帧失败或相机中断时，立即回退语音模式，不结束会话。

### 6.3 能力表达边界

当前实现是在服务端接受一轮视频话语后请求单帧图片，并非连续视频流理解。因此：

- 界面可表达“镜头已开启”。
- 不显示“持续观察中”“实时追踪中”等容易误导的文案。
- 识别状态应在实际请求画面后短暂出现。
- 第一阶段仍保持现有按需取帧策略。
- 后续若实现连续采样，需要独立评估带宽、耗电、隐私和后端处理能力。

## 7. 结构化实时结果

工具调用开始时，软体核心缩小，底部结果层出现。结果层不抢占整个屏幕，语音继续播放。

首批结果卡：

- 天气：地点、当前温度、体感和短时趋势。
- 搜索/知识：标题、两到三条摘要和来源入口。
- 图片：大图、简短标题和保存操作。
- 记忆：缩略图、标题、创建时间与“已保存”状态。
- 待办：标题、提醒时间、完成状态。

结构化事件缺失时回退为简短文字状态，不从自然语言文本中猜测卡片字段。

## 8. 动作回执

保存记忆和创建待办必须遵循同一反馈结构：

1. 用户明确发出动作指令。
2. 界面显示低干扰的执行中状态。
3. 服务端确认成功后出现回执卡。
4. 助手用一句话同步确认。
5. 失败时说明未完成，并给出一次重试操作。

示例：

- “已保存到记忆 · 65W GaN 充电器”
- “已创建待办 · 周一 09:00 带充电器”

不得只依赖助手自然语言声称“已经保存”；UI 回执必须来自真实工具结果或专用事件。

## 9. 会话连续性

语音、视频、图片、工具结果、记忆引用和待办引用都回到同一条会话时间线。

- 历史对话详情页提供“继续语音”入口。
- 新实时会话创建后保存服务端返回的 `conversation_id`。
- 从历史对话进入实时模式时传入原有 `conversation_id`。
- 通话结束后回到该对话，而不是返回空首页。
- 对话详情中显示已创建的记忆和待办小标签，可跳转到对应详情。

现有客户端尚未接通这条链路，但现有实时会话与服务端协议已具备 `conversation_id` 基础。

## 10. 实施优先级（已选 A）

### 第一阶段：高价值对齐

1. 语音软体核心、状态动效与真实音量联动。
2. 临时字幕、自然打断和简化控制栏。
3. 历史会话继续语音，结束后回到同一会话。
4. 工具结构化结果卡。
5. 记忆与待办的可靠动作回执。

### 第二阶段：视频交互升级

1. 允许在语音通话中由用户主动开启或关闭镜头。
2. 软体核心与全屏相机之间使用连续过渡。
3. 扩展客户端与服务端协议，使会话模式可以在进行中升级。

### 第三阶段：能力成熟后再开放

- 持续视觉采样或视频理解。
- 更接近全双工的听说策略。
- 后台和锁屏通话。
- 多音色与智能等级设置。

第三阶段功能在真实可用前不得先放置占位控制。

## 11. 技术约束

- Android APK 是本次唯一移动端实现目标。
- iOS 代码保留但冻结，不修改、不扩展。
- Responses API 是唯一允许使用的 Agent API 协议。
- 服务端变更只能在 `140.143.229.103:8700` 对应环境中排查和部署。
- 客户端必须保留现有鉴权、记忆、待办与历史数据兼容性。
- 通话中开启镜头不是纯 UI 改动，需要客户端和服务端协议共同支持。
- 结构化结果卡不得直接渲染未校验的任意 JSON；需定义受控卡片类型和回退行为。

## 12. 错误与恢复

- 连接失败：保留当前上下文，提供重试和结束两个操作。
- 工具失败：结果层显示失败原因与重试，不生成成功回执。
- 相机权限拒绝：继续保持语音模式，并提供系统设置入口。
- 相机采帧失败：说明暂时看不到画面，不中断语音会话。
- 保存或待办失败：不在本地先显示永久成功状态。
- 应用回到前台：若会话已经失效，落回原对话并保留已有内容。

## 13. 验收标准

### 体验验收

- 用户从冷启动到开始语音不超过一次主操作。
- 相机不会在未经用户点击的情况下启动。
- 语音、思考、工具和回答状态可仅通过形态与短文案区分。
- 用户开口能可靠中断当前输出。
- 工具结果出现时音频不会被页面跳转中断。
- 每次保存记忆和创建待办都有来自真实结果的回执。
- 结束通话后能在同一对话中查看内容并继续语音。
- 视频模式中画面不被大型软体或持久面板遮挡。

### 工程验收

- Android 构建、现有功能测试和 realtime 冒烟测试通过。
- iOS 目录无变更。
- Agent 调用仍只使用 Responses API。
- 新的结构化事件具备版本与未知类型回退。
- 中途开关镜头不创建新的会话 ID。
- 断网、权限拒绝、工具失败和采帧失败均有可恢复路径。

## 14. 非目标

- 不逐像素复制品牌标志、字体资产或专属图形资源。
- 不在本轮增加社交、社区或多人协作功能。
- 不把首页改造成任务管理仪表盘。
- 不自动保存用户看到的内容。
- 不在能力未实现时用静态动画假装持续理解或全双工。
